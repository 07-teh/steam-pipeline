# Steam Player Count Tracker

**English** | [中文](README-cn.md)

A script that collects the number of online players for a list of Steam games. It runs automatically on GitHub Actions every 3 hours, rotating its start hour so that every hour of the day is covered once every 3 days. Data is stored in SQLite.

[![Fetch Steam player counts](https://github.com/07-teh/steam-pipeline/actions/workflows/fetch.yml/badge.svg)](https://github.com/07-teh/steam-pipeline/actions/workflows/fetch.yml)

## Why I built this

I'm a long-time NARAKA: BLADEPOINT player. Over the past few years, matchmaking has been taking longer and longer, and it feels like players are leaving. I wanted to know how many people actually play it each day, and which hours are the busiest, so I can play during peak hours and wait less for a match.

I also track a few soulslike games I play and some popular titles, including several of the biggest games on Steam. Together they give a rough sense of how many people play the top games on a normal day. So far, Counter-Strike 2 is far ahead every single time.

It's also a hands-on project to build my practical skills.

## How it works

1. Connect to the database, and create the table and view if they don't exist yet.
2. Record the current time in UTC.
3. Fetch the player count for each game from Steam, in list order.
4. Retry on failure: up to 3 attempts, waiting 2 seconds and then 4 seconds between them (exponential backoff).
5. Save one record per game, whatever the result:
   - Success: status `ok`, with the player count.
   - Steam returned no valid data: status `no_data`, player count left empty.
   - Still failing after retries: status `failed`, player count left empty.
6. Pause 1 second after each game to avoid sending requests too quickly.
7. When every game is done, Actions commits the updated `steam.db` back to the repo and shuts down the virtual machine.

If every game fails, the script exits with code 1 so the Actions run shows up as failed and GitHub sends an email. The failed records are still committed.

## Running locally

The first time, set up a virtual environment and install the dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

After that, activate the virtual environment (VS Code's built-in terminal does this automatically) and run:

```bash
python fetch_players.py
```

Note: running locally modifies `steam.db`. Before committing, restore it with `git checkout -- steam.db` to avoid conflicts with the automatic commits from Actions.

## Data

Records are stored in the `player_counts` table:

| Column | Description |
|------|------|
| id | Auto-increment primary key |
| app_id | Steam app ID. Stays the same even if the game is renamed |
| game_name | Game name, maintained by hand in the script |
| player_count | Online players. Empty (NULL) when status is not `ok` |
| fetched_at | Fetch time in UTC, ISO 8601 format |
| status | `ok` / `no_data` / `failed` |

There is also a view, `player_counts_local`, which converts the fetch time to Malaysia time (UTC+8) and can be queried directly.

**Why store time in UTC:** The script normally runs on GitHub Actions, on a machine in the US. When I run it by hand, it's Malaysia time. If each run stored its own local time, the data would mix time zones and comparisons would easily go wrong. Storing everything in UTC keeps all records on the same standard. For Malaysia time, query the `player_counts_local` view.

**Why a status column:** 0 is real data. It means nobody was online at that moment. If `no_data` or `failed` were also stored as 0, there would be no way to tell "nobody was playing" apart from "we never got the number". Those fake zeros would drag averages down and cause large errors.

## Findings

### When is NARAKA: BLADEPOINT busiest?

![Average online players of NARAKA: BLADEPOINT by hour](charts/naraka_hourly.png)

- **7 PM to 11 PM is the busiest time**, with 46,000 to 71,000 players on average. Numbers start dropping after 10 PM.
- **5 AM to 8 AM is the quietest**, with only 5,000 to 8,000 players on average, less than a fifth of the peak.
- To wait less for a match, play between 7 PM and 11 PM.

**About this data:**

- Date range: 2026-09-23 to 2026-10-15 (Malaysia time), 85 fetches in total.
- Suspicious zeros are excluded (see "Six games returned 0 at the same time" below).
- Bars marked *Fewer than 3 samples* in the legend have fewer than 3 data points for that hour, so their averages are less reliable.
- There is no data yet for 3 AM, 9 AM, 1 PM and 5 PM. With the new schedule (see "GitHub Actions scheduled runs are not on time" below), these hours will fill in over time.
- Cached values returned by Steam have not been deduplicated yet. That's the next step.

The chart is generated by `analyze.py`. Run it again to update the chart with the latest data:

```bash
python analyze.py
```

## Problems I ran into

### NARAKA request failed (2026-09-23)

**What happened:** While I was still writing the script, before uploading it to GitHub, fetching NARAKA: BLADEPOINT failed with `Errno 61 Connection refused`. The error happened while opening the connection, so the request was never sent. It could have been a network glitch, or Steam refusing the connection for a moment.

**Diagnosis:** Running it again about a minute later worked, so I concluded it was a transient failure, not a problem with the code or the API.

**Fix:** Added retries: wait 2 seconds, then 4 seconds, for up to 3 attempts. I haven't seen the problem since.

### Steam returns cached values (2026-09-23)

**What happened:** When I had AI check the data, it noticed that Counter-Strike 2 returned exactly the same player count in three fetches within 10 minutes. Wallpaper Engine did the same.

**Diagnosis:** This Steam API returns cached values, not real-time data.

**Fix:** Raw data is kept as is, and deduplication is left for the analysis step, so no original records are lost. Data collection is still ongoing, and deduplication will be added later.

### Pushed without testing and broke Actions (2026-09-24)

**What happened:** When adding the local time view, I asked AI to write the SQL because I'm not familiar with it. Its code had a `CREATE TABLE` with `...` as a placeholder for me to fill in the columns. I didn't notice, pasted it and pushed, and the Actions run failed when I triggered it by hand.

**Fix:** I found the placeholder was the cause, filled in the full column definitions and committed again. Everything was back to normal 6 minutes later.

**Lesson:** I now run the script locally before every push.

### Six games returned 0 at the same time (2026-10-11)

**What happened:** In the fetch at 2026-10-11 17:08 UTC, Apex Legends, GTA V, ELDEN RING, FINAL FANTASY VII, WARDOGS and Wallpaper Engine all returned 0 players, yet their status was `ok`. The other 9 games were normal. These 6 records are the only zeros in the whole database, and all of them come from this one run.

| Fetch time (UTC) | Apex Legends | ELDEN RING |
|------|------|------|
| 10-11 11:54 | 155,744 | 32,955 |
| 10-11 17:08 | **0** | **0** |
| 10-11 21:19 | 66,837 | 28,231 |

**Diagnosis:** These zeros are almost certainly fake:

- A game with tens of thousands of players can't suddenly drop to zero and recover a few hours later.
- Six games went to 0 at the exact same moment while the other 9 were fine. That looks like Steam returned bad data that one time, not like players actually left.

The status is `ok` because Steam returned `result == 1`, so the script treated the query as valid.

**Fix:** Raw data is kept unchanged and filtered during analysis instead. I didn't handle this in the fetch script for two reasons:

- At fetch time, the script can't tell a real 0 from a fake one. Smaller games really can have 0 players at some hours.
- Filtering during analysis can be undone, and the rules can change any time. Changing the data in the script would lose the original records for good.

**Lesson:** A status of `ok` doesn't mean the number is right. Even when an API says it succeeded, check that the values make sense.

### GitHub Actions scheduled runs are not on time (2026-10-14)

**What happened:** The original schedule, `0 */6 * * *`, should run at 0, 6, 12 and 18 UTC. In practice, runs were often late, by up to almost 3 hours (the 10-14 00:00 run started at 02:58), and some were skipped entirely (the 10-13 12:00 run never happened).

**Diagnosis:** From what I observed, this is a limitation of GitHub Actions itself. Free scheduled jobs share one queue, and GitHub doesn't guarantee they run on time. The top of the hour is when the most people in the world schedule jobs, so with so many triggered at once, it's the most crowded and least reliable time.

**Fix:**

- Moved the minute to 13, away from the busy top of the hour.
- Changed to every 3 hours, split into 3 groups that rotate by date: group 1 starts at hour 0, group 2 at hour 1, group 3 at hour 2. Every hour of the day gets covered once every 3 days. The old schedule only hit the same 4 times each day, and other hours were sampled only when a run happened to be late.

**Trade-off:** Runs per day went from 4 to 8. Since each run commits the whole `steam.db`, the repo will grow faster. I plan to switch the data to CSV later.

**Lesson:** Free scheduling services aren't always reliable. Schedule design has to account for the platform's limits.

## Limitations and next steps

**Current limitation:** Only player counts are collected, which limits what the data can show.

**Plans:**

- Add more dimensions such as achievements and reviews, and build a mature, sustainable monitoring setup.
- Every quarter, and before and after each major Steam sale, produce a full report with charts, such as the top 50 games by online players and the most-played games released in 2026.
- Steam publishes similar statistics, but few people look for them and the information is scattered. A report like this could help sellers of game merchandise see which games are popular right now and plan what to sell. It can't predict anything, though. It can only help them follow up after a game has already taken off.
